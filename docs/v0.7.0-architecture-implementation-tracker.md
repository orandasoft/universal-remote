## Current architecture state

### Protocol architecture

The protocol-neutral receive contracts live in:

    custom_components/universal_remote/protocols/base.py

Concrete NEC and NEC1-F16 behavior lives in:

    custom_components/universal_remote/protocols/nec.py

The explicit authoritative registry lives in:

    custom_components/universal_remote/protocols/registry.py

The registry supplies deterministic decoder-family ordering for receiver events
and learning. Received and codeset-generated commands use the same handler
normalization.

Protocol handlers own optional:

- receive decoding;
- normalized identity generation;
- repeat-frame decoding;
- repeat-association timing policy;
- learning confidence and labels;
- privacy-safe diagnostic metadata.

Generic `event.py` no longer contains an NEC-specific repeat-association
timeout. Registry validation rejects invalid repeat-policy declarations.

### Profile and device-type architecture

Immutable profile contracts live in:

    custom_components/universal_remote/profiles/base.py

The authoritative profile and capability registry lives in:

    custom_components/universal_remote/profiles/registry.py

Profiles own:

- stable profile and stored device-type IDs;
- deterministic device-type ordering;
- user-facing device-type labels;
- supported Home Assistant entity domains;
- ordered command roles;
- source rules;
- presentation overrides;
- optional capability references.

Device-type discovery and validation no longer depend on the presence of a
codeset. A fake non-generic profile with no codeset proves that a future device
type can be configured independently of fixed command-library availability.

### Capability architecture

The Japanese tuner capability lives in:

    custom_components/universal_remote/profiles/capabilities/japanese_tuner.py

`TunerCapability` owns:

- tuner declarations and selector aliases;
- numeric ranges;
- tuner availability;
- tuner-aware numeric routing;
- tuner inference;
- sent and received state-update policy;
- tuner command presentation.

Stable tuner IDs may differ from configured selector command names. The select
entity exposes the stable ID while `UniversalRemoteRuntime.async_select_tuner()`
resolves and sends the configured selector alias. State changes occur only
after successful transmission.

The fake `FM` tuner with selector command `RADIO` verifies that the runtime and
select entity are not tied to Japanese command names.

### Codeset architecture

The immutable codeset registry lives in:

    custom_components/universal_remote/codesets.py

Codesets supply declarative setup-time bindings to:

- an `infrared-protocols` enum;
- a base profile;
- an optional decoder family;
- ordered capabilities.

The `lg_tv_jp` codeset supplies the television profile and the
`japanese_tuner` capability. Other television codesets and manually configured
televisions do not gain Japanese tuner behavior from command names alone.

Codesets do not determine whether a device type exists and are not active
runtime processors.

### Setup-time resolved models

Semantic profile resolution and receiver resolution live in:

    custom_components/universal_remote/resolved.py

The per-entry aggregate is:

    UniversalRemoteData
    ├── resolved_profile
    ├── resolved_receiver
    └── runtime

`ResolvedRemoteProfile` owns immutable Home Assistant semantics:

- base profile;
- retained codeset definition, when compatible;
- deterministic ordered capabilities;
- merged command presentation.

`ResolvedReceiverModel` owns immutable receive bindings:

- decoder-family identity;
- ordered receive handlers;
- codeset-generated normalized match maps;
- supported receiver event types.

`UniversalRemoteRuntime` owns operational sending data and mutable per-entry
state:

- infrared emitter identity;
- copied configured-command mapping;
- tuner capability;
- selected tuner;
- send synchronization.

Receiver-only entries retain resolved profile and receiver models without
creating a sending runtime.

Normal signal handling no longer:

- resolves a decoder family through the codeset registry;
- loads an infrared-library enum;
- rebuilds codeset match maps;
- derives receiver event types.

Those operations occur during config-entry setup.

### Runtime boundaries

The outbound fixed-command path remains:

    Home Assistant entity action
    -> profile or capability resolves a named command
    -> configured stored payload
    -> protocol-neutral infrared emitter send

After payload resolution, sending does not consult receive handlers or codeset
enums.

The inbound named-command path remains:

    received signal
    -> resolved receive handler
    -> normalized protocol identity
    -> immutable codeset match map
    -> optional named command
    -> profile and capability semantics
    -> Home Assistant event and assumed-state update

Profiles do not inspect raw timings or protocol identity fields. Receive
handlers do not parse stored payloads or send commands.

### Receiver-event behavior

Receiver behavior is now documented consistently:

- no supported codeset: `unknown` with timing metadata;
- selected decoder family recognizes an unmatched command: protocol event such
  as `nec` or `nec1_f16`;
- normalized identity matches a codeset member: friendly named event such as
  `power` or `volume_up`;
- malformed or unsupported signal: `unknown`.

The documentation correction did not change runtime behavior.

### Future stateful-command boundary

v0.7.0 intentionally implements discrete named-command remotes.

Some devices, especially climate devices, encode complete mutable state in each
infrared frame. Future support should add a parallel stateful command model or
adapter that can:

- construct an `infrared-protocols` command from semantic device state;
- decode an incoming stateful command into semantic device state;
- describe supported state fields;
- remain independent of Home Assistant entity instances.

That future layer can reuse the completed profile registry, device-type catalog,
capabilities, resolved setup model, and infrared emitter/receiver boundaries.
It must not represent every state combination as a large fixed command map.

No speculative climate API is included in v0.7.0.

### Profile-aware diagnostics

Diagnostics now derive television source counts from the configured profile.

Consequently:

- a generic profile reports `source_count: 0` even when commands such as
  `HDMI_1` are configured;
- a television profile reports source counts using the same normalized source
  rules as the media-player platform;
- a receiver-only television remote may report configured source semantics
  while `media_player_expected` remains false because no emitter is linked;
- command counts, button counts, command-name reporting, and payload redaction
  remain unchanged.

This closes the remaining profile-awareness inconsistency in diagnostics.
