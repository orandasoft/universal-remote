## Current architecture state

### Protocol architecture

The protocol-neutral receive-side contracts are located in:

    custom_components/universal_remote/protocols/base.py

The concrete NEC and NEC1-F16 implementation is located in:

    custom_components/universal_remote/protocols/nec.py

The authoritative protocol registry is located in:

    custom_components/universal_remote/protocols/registry.py

It supplies all receive and learning handlers and defines deterministic
decoder-family ordering. Receiver-event and learning orchestration consume the
same registry without concrete NEC-family decision logic.

### Profile architecture

The immutable profile contracts are located in:

    custom_components/universal_remote/profiles/base.py

They include:

- `DeviceProfile`;
- `CommandRole`;
- `SourceRule`;
- `CommandPresentation`;
- `ProfileCapability`;
- explicit entity-domain declarations;
- ordered stable capability IDs.

The production generic and TV profiles are located in:

    custom_components/universal_remote/profiles/generic.py
    custom_components/universal_remote/profiles/tv.py

The authoritative profile and capability registry is located in:

    custom_components/universal_remote/profiles/registry.py

It provides deterministic registration, lookup, structural validation, and
validation of profile capability references.

Profile role and source resolution is located in:

    custom_components/universal_remote/profiles/resolver.py

Media-player eligibility, roles, sources, command-UI source classification, and
diagnostics source counting are resolved from profile declarations.

### Capability architecture

The Japanese television tuner capability is located in:

    custom_components/universal_remote/profiles/capabilities/japanese_tuner.py

It owns:

- stable capability ID `japanese_tuner`;
- tuner order `DTV`, `BS`, `CS1`, `CS2`, `BS4K`, and `CS4K`;
- keypad numbers 1 through 12;
- selector alias resolution;
- tuner-specific numeric-command resolution;
- available-tuner detection;
- selected-tuner keypad routing;
- tuner implication from sent and received commands;
- explicit sent-success and received-match update policies.

The capability is globally registered but is not attached unconditionally to
the base TV profile.

### Codeset architecture

The authoritative codeset definitions and bindings are located in:

    custom_components/universal_remote/codesets.py

Each immutable codeset definition owns:

- stable codeset ID;
- user-facing label;
- infrared-library module and enum class;
- base profile ID;
- optional receive decoder-family ID;
- ordered capability IDs.

The codeset registry validates duplicate IDs and missing profile,
decoder-family, and capability references.

All existing codesets retain their current TV profile and receive-decoder
bindings. The regional `japanese_tuner` capability is bound specifically to
`lg_tv_jp`.

`infrared_library.py` remains the compatibility and payload-generation facade.
Generated and persisted Pronto payload behavior remains unchanged.

### Resolved semantic model

Setup-time semantic resolution is located in:

    custom_components/universal_remote/resolved.py

`ResolvedRemoteProfile` contains:

- the resolved base `DeviceProfile`;
- the selected `CodesetDefinition`, when retained;
- the deterministic ordered `ProfileCapability` objects;
- capability lookup by stable capability ID.

`resolve_remote_profile()` preserves the existing configuration precedence:

1. A valid codeset supplies its bound profile when the stored device type is
   absent, invalid, or generic.
2. A codeset is retained when its profile matches the explicit stored profile.
3. A conflicting explicit non-generic profile wins and discards the codeset.
4. An unknown or stale codeset is ignored.
5. An absent or invalid device type falls back to the generic profile.
6. A custom registry without an applicable generic fallback resolves to no
   semantic model.

The resolver is pure and independent of Home Assistant entities and services.

### Setup-time runtime data

Config-entry setup now resolves the semantic model after normalizing the stored
remote definition.

`UniversalRemoteData` stores:

- the existing `UniversalRemoteRuntime`, when an emitter is configured;
- the resolved profile, codeset, and capability model.

Receiver-only entries therefore receive resolved semantics even though they do
not create a sending runtime.

The resolved model is currently informational. Existing platforms and runtime
behavior do not yet consume it.

### Command-name dependency boundary

Protocol-neutral command-name normalization and configured-command lookup are
located in:

    custom_components/universal_remote/command_names.py

This prevents dependency cycles between generic helpers, infrared-library
metadata, codesets, profiles, and capabilities.

`helpers.py` retains explicit compatibility re-exports for existing callers.

### Compatibility and remaining boundaries

Stored `device_type`, `codeset`, command objects, and persisted payloads remain
unchanged.

`UniversalRemoteRuntime` still owns the legacy Japanese tuner constants,
available-tuner detection, keypad routing, and selected-tuner state updates.

`select.py` still creates and operates its tuner select through the runtime's
legacy tuner API.

The following areas remain pending:

- passing the resolved tuner capability into `UniversalRemoteRuntime`;
- replacing runtime tuner constants and decisions with capability methods;
- preserving send-success and received-match state semantics;
- capability-driven tuner-select creation and operation;
- migration of remaining consumers to the resolved semantic model;
- removal of obsolete tuner-specific runtime decisions after parity is proven.

## Requirement progress

### Implemented and verified in the protocol-registry slice

- One authoritative registry supplies receive and learning handlers.
- Decoder-family order is explicit and deterministic.
- Received and codeset-generated commands share handler normalization.
- Event and learning orchestration are protocol-neutral.
- NEC and NEC1-F16 behavior and command identity remain covered.
- Repeat handling, diagnostics, and learning metadata are handler-owned.

### Implemented and verified in the profile-registry slices

- Immutable generic profile contracts have been introduced.
- Generic and television profiles are explicitly registered.
- Profile lookup by ID and stored device type is deterministic.
- Media-player eligibility, roles, sources, and diagnostics are profile-driven.
- Duplicate and invalid profile definitions are rejected.
- Existing media-player behavior remains unchanged.

### Implemented and verified in the capability-contract slice

- A generic immutable capability contract has been introduced.
- Capability definitions are explicitly and deterministically registered.
- Duplicate capability IDs and missing references are rejected.
- Japanese tuner semantics are isolated in a tuner capability.
- Available-tuner detection and numeric routing preserve existing behavior.
- A fake non-TV capability works without registry decision-logic changes.
- Japanese tuner behavior is not attached to every TV profile.

### Implemented and verified in the codeset-registry slice

- Codeset metadata has an authoritative immutable registry.
- Codesets bind deterministically to profiles, decoder families, and
  capabilities.
- `lg_tv_jp` alone receives the regional `japanese_tuner` capability.
- Existing receive-capable codesets retain their decoder-family bindings.
- Invalid profile, decoder-family, and capability references are rejected.
- Registry mappings are immutable and registration order is inspectable.
- Existing payload generation, receiving, persistence, and entity behavior are
  unchanged.

### Implemented and verified in the resolved-profile slice

- An immutable resolved remote semantic model has been introduced.
- Manual remotes resolve from their stored device type.
- Codesets resolve through their authoritative profile and capability bindings.
- `lg_tv_jp` resolves the TV profile and `japanese_tuner`.
- Other TV codesets do not receive the regional capability.
- Profile capabilities precede codeset additions without duplicate objects.
- Unknown and stale codesets are ignored deterministically.
- Conflicting explicit non-generic device types preserve existing precedence by
  discarding the codeset.
- Invalid or absent device types fall back to the generic profile.
- Fake profiles, codesets, and capabilities resolve through generic logic.
- The resolved model is stored in config-entry runtime data for both
  emitter-backed and receiver-only entries.
- Existing operational runtime and entity behavior remains unchanged.

### Quality requirements

- `Q-001`: v0.6.1 behavior remains covered by the complete regression suite.

## Next implementation slice

Migrate Japanese tuner behavior inside `UniversalRemoteRuntime` to the resolved
`tuner` capability while preserving the runtime and select APIs used by current
platforms.

The checkpoint should:

1. Allow `UniversalRemoteRuntime` to receive an optional `TunerCapability`.
2. Pass the resolved `japanese_tuner` capability from config-entry setup only
   when it is present in the resolved semantic model.
3. Derive `available_tuners` through the capability contract.
4. Route generic `NUM_n` commands through the capability and currently selected
   tuner.
5. Derive selected-tuner changes from capability selector and prefixed numeric
   command rules.
6. Preserve the existing rule that tuner state changes only after a successful
   send.
7. Preserve received-command tuner-state synchronization.
8. Keep the current runtime properties, listener behavior, and select-platform
   interface stable.
9. Add explicit tests showing that:
   - `lg_tv_jp` receives tuner behavior;
   - other TV codesets do not;
   - a manual TV without the capability does not gain regional behavior;
   - a fake tuner capability works without runtime decision-logic changes;
   - failed sends do not update selected tuner state.
10. Remove the hardcoded tuner constants and command-name decisions from
    `runtime.py` only after all parity tests pass.
11. Preserve 100% coverage and every unrelated regression test.

Do not migrate `select.py` to consume the resolved semantic model directly in
the same checkpoint. It should continue using the stable runtime tuner API
until runtime capability migration is independently green.
