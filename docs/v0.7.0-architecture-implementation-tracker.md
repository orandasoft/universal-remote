## Current architecture state

### Protocol architecture

The protocol-neutral receive-side contracts are located in:

    custom_components/universal_remote/protocols/base.py

The concrete NEC and NEC1-F16 handlers are located in:

    custom_components/universal_remote/protocols/nec.py

The authoritative protocol registry is located in:

    custom_components/universal_remote/protocols/registry.py

It supplies receive and learning handlers and defines deterministic
decoder-family ordering. Receiver-event and learning orchestration consume the
same registry without concrete NEC-family decision logic.

### Profile architecture

The immutable profile contracts are located in:

    custom_components/universal_remote/profiles/base.py

They include:

- `DeviceProfile`;
- `CommandRole`;
- `SourceRule`;
- `CommandPresentation`;
- `ProfileCapability`;
- entity-domain declarations;
- ordered stable capability IDs.

The production generic and television profiles are located in:

    custom_components/universal_remote/profiles/generic.py
    custom_components/universal_remote/profiles/tv.py

The authoritative profile and capability registry is located in:

    custom_components/universal_remote/profiles/registry.py

Media-player eligibility, roles, sources, command presentation, and diagnostics
source counting are resolved from profile declarations.

### Capability architecture

The Japanese television tuner capability is located in:

    custom_components/universal_remote/profiles/capabilities/japanese_tuner.py

`TunerCapability` owns:

- stable capability identity;
- ordered tuner declarations;
- selector aliases;
- valid numeric keypad values;
- available-tuner detection;
- selected-tuner keypad routing;
- tuner implication from selector and prefixed-number commands;
- sent-success state-update policy;
- received-match state-update policy.

The production Japanese tuner capability declares:

- `DTV`;
- `BS`;
- `CS1`;
- `CS2`;
- `BS4K`;
- `CS4K`;
- keypad numbers 1 through 12.

The capability is registered globally but is not attached to every television
profile.

### Codeset architecture

The authoritative codeset definitions and bindings are located in:

    custom_components/universal_remote/codesets.py

Codesets bind deterministically to:

- a base profile;
- an optional receive decoder family;
- ordered capability IDs.

The regional `japanese_tuner` capability is attached specifically to
`lg_tv_jp`. Other television codesets do not receive it.

The codeset registry validates duplicate definitions and missing profile,
decoder-family, and capability references.

### Resolved semantic model

Setup-time semantic resolution is located in:

    custom_components/universal_remote/resolved.py

`ResolvedRemoteProfile` contains:

- the resolved base profile;
- the retained codeset definition, when applicable;
- deterministic ordered capability objects.

Resolution preserves the existing configuration precedence:

1. A valid codeset may supply its bound profile when the stored type is absent,
   invalid, or generic.
2. A matching explicit profile retains the codeset.
3. A conflicting explicit non-generic profile wins and discards the codeset.
4. An unknown codeset is ignored.
5. An absent or invalid device type falls back to the generic profile.

The resolved model is stored in `UniversalRemoteData` for both sending and
receiver-only entries.

### Capability-driven runtime

`UniversalRemoteRuntime` accepts an optional `TunerCapability`.

When no tuner capability is supplied:

- `available_tuners` is empty;
- regional `NUM_n` overlay routing is disabled;
- selector and prefixed-number names do not alter tuner state;
- unrelated remote command behavior is unchanged.

When a tuner capability is supplied:

- available tuners come from `TunerCapability.available_tuners()`;
- generic keypad routing uses
  `TunerCapability.routed_keypad_command_name()`;
- selector and prefixed-number state inference uses
  `TunerCapability.implied_tuner()`;
- sent tuner changes occur only after successful transmission and only when
  `update_after_sent_success` is enabled;
- received tuner changes occur only when
  `update_after_received_match` is enabled.

The runtime no longer owns Japanese tuner IDs, number ranges, prefixed-command
construction, or tuner-specific command-name recognition.

A fake tuner capability with non-Japanese tuner IDs and keypad values exercises
the same runtime path without runtime decision-logic changes.

### Setup-time capability injection

Config-entry setup retrieves `japanese_tuner` from the resolved semantic model,
verifies that it is a `TunerCapability`, and passes it to the sending runtime.

Consequently:

- `lg_tv_jp` enables Japanese tuner behavior;
- other television codesets do not enable it;
- a manually configured television does not gain regional tuner behavior merely
  because similarly named commands exist;
- receiver-only entries retain resolved semantic information without creating a
  sending runtime.

### Capability-aware command presentation

Capability-aware presentation is resolved through the same setup-time semantic
model used by the runtime.

`ProfileCapability.presentation()` provides an optional generic capability
contract. The default implementation does not claim presentation semantics.

`TunerCapability.presentation()` derives tuner presentation from its declared:

- tuner IDs;
- selector aliases;
- supported numeric values.

It supplies presentation for:

- selector commands, including aliases;
- tuner-prefixed numeric commands.

The capability does not depend on a fixed list of Japanese tuner IDs.

`ResolvedRemoteProfile.presentation()` merges presentation in deterministic
precedence order:

1. profile-specific presentation overrides;
2. ordered resolved capabilities.

Earlier sources retain precedence for fields they define. Later sources may
fill missing label, icon, or category fields.

The public command UI helpers accept optional resolved semantic context:

- `command_label()`;
- `command_icon()`;
- `command_category()`.

Without resolved context, their existing context-free fallback behavior remains
available. Prefixed numeric fallback recognition is generic and is no longer
restricted to `DTV`, `BS`, `CS1`, `CS2`, `BS4K`, and `CS4K`.

Button setup retrieves `resolved_profile` from `UniversalRemoteData` and passes
it into command label and icon resolution.

A fake tuner capability using `RADIO`, `FM`, and `FM_NUM_7` verifies that the
presentation path does not require Japanese tuner IDs or changes to generic
command UI decision logic.

### Stable platform boundary

The tuner-select platform remains unchanged and continues using the stable
runtime interface:

- `available_tuners`;
- `selected_tuner`;
- tuner-state listeners;
- `async_send_command_name()`.

Its behavior is now capability-driven through the runtime rather than through
hardcoded runtime command-name rules.

Remote, button, media-player, event, and integration tests explicitly provide
the tuner capability when they exercise tuner-aware direct-runtime behavior.

### Compatibility

The following remain unchanged:

- stored `device_type` and `codeset` values;
- stored command objects;
- generated and persisted command payloads;
- infrared transmission APIs;
- remote and button service behavior;
- tuner-select public behavior;
- media-player source synchronization behavior;
- event-driven received-command synchronization;
- entity unique IDs and device associations.

### Remaining architecture boundaries

The core protocol, profile, capability, codeset, setup-time resolution, tuner
runtime, and command-presentation migrations are complete.

The audit found no remaining tuner-specific decision logic in:

- `select.py`;
- media-player tuner synchronization;
- diagnostics;
- remote sending;
- button sending.

The tuner names retained in the television profile are declarative source data,
not generic runtime or platform decision logic.

Remaining work should focus on:

- aligning user and architecture documentation with capability-driven behavior;
- documenting setup-time profile, codeset, and capability resolution;
- correcting documentation that still describes tuner support as being inferred
  solely from configured command names;
- completing the separate persisted `0xFE04` investigation;
- final release-readiness review.

## Requirement progress

### Implemented and verified: protocol registry

- One authoritative registry supplies receive and learning handlers.
- Decoder-family order is explicit and deterministic.
- Received and codeset-generated commands share handler normalization.
- Event and learning orchestration are protocol-neutral.
- NEC and NEC1-F16 behavior and identity remain covered.
- Repeat handling, diagnostics, and learning metadata are handler-owned.

### Implemented and verified: profile registry

- Immutable generic profile contracts are registered explicitly.
- Generic and television profile lookup is deterministic.
- Media-player eligibility, roles, sources, and diagnostics are profile-driven.
- Invalid and duplicate definitions are rejected.
- Existing media-player behavior remains unchanged.

### Implemented and verified: capability contracts

- Capability definitions are immutable and explicitly registered.
- Japanese tuner semantics are isolated in `TunerCapability`.
- Available-tuner detection, numeric routing, tuner inference, and state-update
  policies are capability-owned.
- Fake non-TV tuner semantics work through the same generic contract.
- Japanese tuner behavior is not attached to every television.

### Implemented and verified: codeset registry

- Codeset metadata has one authoritative immutable registry.
- Codesets bind to profiles, decoder families, and capabilities.
- `lg_tv_jp` alone receives the production Japanese tuner capability.
- Invalid references and duplicate definitions are rejected.
- Existing payload generation and persistence remain unchanged.

### Implemented and verified: resolved semantic model

- Manual remotes resolve from their stored device type.
- Codesets resolve through authoritative bindings.
- Ordered capabilities resolve without duplicate objects.
- Stale and conflicting configuration behavior is deterministic.
- Resolved semantics are stored in config-entry runtime data.
- Receiver-only entries receive resolved semantics.

### Implemented and verified: capability-driven tuner runtime

- `UniversalRemoteRuntime` accepts an optional `TunerCapability`.
- Runtime tuner availability is capability-derived.
- Runtime keypad overlay routing is capability-derived.
- Sent tuner changes occur only after successful sends.
- Sent and received state-update policies are capability-controlled.
- No-capability runtimes do not infer regional tuner behavior from command
  names.
- `lg_tv_jp` setup injects the tuner capability.
- Other television codesets and manual televisions do not gain the regional
  capability.
- Existing tuner-select, media-player, remote, button, and event interfaces
  remain stable.
- Hardcoded Japanese tuner constants and recognition logic have been removed
  from `runtime.py`.
- A fake tuner capability proves that runtime behavior is not tied to Japanese
  tuner IDs or number ranges.

### Implemented and verified: capability-aware command presentation

- Capabilities may provide command-specific presentation without changing
  generic command UI helpers.
- `TunerCapability` derives selector and tuner-number presentation from its
  declared tuner rules and numeric values.
- `ResolvedRemoteProfile` merges profile and ordered capability presentation
  deterministically.
- Profile presentation fields take precedence while capabilities may fill
  missing fields.
- Button setup consumes the resolved semantic model.
- Existing context-free command label, icon, and category behavior remains
  available.
- Generic prefixed numeric commands no longer depend on a fixed Japanese tuner
  prefix list.
- A fake `FM` tuner capability proves that presentation is not tied to Japanese
  tuner IDs.
- `select.py`, media-player synchronization, diagnostics, persistence, runtime
  sending, and entity identifiers remain unchanged.
