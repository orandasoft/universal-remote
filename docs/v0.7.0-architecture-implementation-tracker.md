## Current architecture state

### Protocol architecture

The protocol-neutral receive-side contracts are located in:

    custom_components/universal_remote/protocols/base.py

They include:

- `NormalizedInfraredCommand`;
- `ProtocolDecodeResult`;
- `ProtocolRepeatResult`;
- `ReceiveProtocolHandler`;
- protocol-neutral command identities and matching keys;
- optional learning metadata, repeat decoding, and diagnostics callbacks.

The concrete NEC and NEC1-F16 implementation is located in:

    custom_components/universal_remote/protocols/nec.py

It owns:

- NEC and NEC1-F16 decoding;
- protocol-neutral normalization;
- repeat recognition;
- safe timing diagnostics;
- learning labels, confidence, and metadata formatting.

The authoritative protocol registry is located in:

    custom_components/universal_remote/protocols/registry.py

It defines:

- all concrete receive and learning handlers;
- deterministic decoder-family order;
- protocol lookup;
- decoder-family lookup;
- validation for duplicate protocol IDs and invalid family references.

Receiver-event orchestration in `event.py` and learning orchestration in
`learn.py` are protocol-neutral. The options flow derives concrete learning
decoder choices from the same registry.

### Profile architecture

The immutable profile contracts are located in:

    custom_components/universal_remote/profiles/base.py

They include:

- `DeviceProfile`;
- `CommandRole`;
- `SourceRule`;
- `CommandPresentation`;
- `ProfileCapability`;
- explicit entity-domain declarations;
- an ordered collection of stable capability IDs.

The production profiles are located in:

    custom_components/universal_remote/profiles/generic.py
    custom_components/universal_remote/profiles/tv.py

They preserve the existing generic and television device types. The TV profile
owns the ordered media-player role aliases and source declarations that were
previously embedded in `media_player.py`, `const.py`, and `command_ui.py`.

The authoritative profile and capability registry is located in:

    custom_components/universal_remote/profiles/registry.py

It provides:

- deterministic profile and capability registration order;
- lookup by stable profile ID;
- lookup by stored device type;
- lookup by stable capability ID;
- ordered capability lookup for a profile;
- duplicate profile-ID and device-type validation;
- duplicate capability-ID validation;
- missing capability-reference validation;
- role, source, capability, and structural validation.

Profile-based command resolution is located in:

    custom_components/universal_remote/profiles/resolver.py

It resolves configured command names against ordered profile role and source
candidates using the same normalized command lookup as existing runtime code.

The media-player platform now:

- selects entity eligibility through the profile registry;
- resolves media-player roles from the selected profile;
- resolves source labels and commands from the selected profile;
- preserves the existing supported-feature calculation;
- preserves the existing assumed-state media-player implementation.

Command-UI source classification and diagnostics source counting use the same TV
profile source declarations. Diagnostics also determines whether a media-player
entity is expected through the selected profile.

### Capability architecture

The Japanese television tuner capability is located in:

    custom_components/universal_remote/profiles/capabilities/japanese_tuner.py

It defines:

- `TunerRule`;
- `TunerCapability`;
- the stable capability ID `japanese_tuner`;
- deterministic tuner order:
  `DTV`, `BS`, `CS1`, `CS2`, `BS4K`, and `CS4K`;
- keypad numbers 1 through 12;
- selector-command alias resolution;
- tuner-specific numeric-command resolution;
- available-tuner detection;
- selected-tuner keypad routing;
- tuner-state implication from selector and prefixed numeric commands;
- explicit sent-command and received-command state-update policies.

The production `japanese_tuner` capability is registered globally in the
profile registry. It is deliberately not attached unconditionally to the base
TV profile.

Japanese tuner behavior is regional codeset behavior. The next codeset-binding
slice will attach it specifically to `lg_tv_jp`, rather than enabling it for
every LG, Samsung, Sharp, Vizio, manually configured, or future television
profile.

The tuner capability contract and its resolver behavior are independently
tested with:

- complete and partial Japanese tuner command sets;
- normalized legacy command names;
- a fake non-TV tuner capability;
- invalid tuners, selector aliases, number ranges, and duplicate declarations;
- missing and duplicate capability registration.

### Compatibility and remaining boundaries

Stored configuration continues to use the existing `device_type` and `codeset`
values. Config flow, options flow, command persistence, codeset import, tuner
runtime, and tuner select behavior have not been migrated.

`runtime.py` still owns the existing Japanese tuner constants and operational
routing. `select.py` still creates its tuner entity from
`runtime.available_tuners`. Those consumers remain unchanged until the
codeset-binding and setup-time resolution layers are complete.

The duplicate `TV_SOURCE_COMMAND_MAP`, `SOURCE_COMMAND_MAPS`, `_ROLE_COMMANDS`,
and local media-player role-resolution implementation have been removed.

The following architecture areas remain pending:

- an authoritative codeset-definition registry;
- codeset-to-profile, decoder-family, and capability bindings;
- binding `japanese_tuner` specifically to `lg_tv_jp`;
- setup-time resolved profile, codeset, and capability models;
- migration of tuner runtime behavior to the resolved capability;
- profile- and capability-driven tuner-select creation;
- migration of remaining entity construction to resolved capabilities;
- completion of codeset metadata separation from `infrared_library.py`.

## Requirement progress

### Implemented and verified in the protocol-registry slice

- `PR-002`: encoding and decoding continue to use `infrared-protocols`.
- `PR-003`: one authoritative registry supplies receive and learning handlers.
- `PR-004`: decoder-family order is explicit and deterministic.
- `PR-005`: normalized command identity is protocol-neutral.
- `PR-006`: received and codeset-generated commands use the same handler
  normalizers for matching.
- `PR-007`: handlers provide optional learning labels, confidence, and
  registry-order priority.
- `PR-008`: repeat recognition and decoding are optional handler behavior.
- `PR-009`: optional diagnostics execute only after command matching fails and
  cannot create a match.
- `PR-010`: generic event and learning orchestration has no concrete
  NEC-specific decision logic.
- `PR-012`: fake non-NEC handlers extend event decoding, learning, and decoder
  selection without generic orchestration changes.
- `PR-013`: handler registration and decoder-family order are explicit,
  deterministic, and inspectable.
- `PR-015`: the handler contract is receive-side only and contains no sending,
  persistence, emitter-selection, or stored-payload responsibilities.
- `PR-016`: capture, decoding, normalization, and learning candidate generation
  are independent of codeset and profile selection.
- `CS-007`: library enum members continue through `to_command()` and the
  existing persisted command format.
- `T-001`: fake non-NEC handlers are exercised through generic event and
  learning paths.
- `T-004`: NEC and NEC1-F16 command identity parity is covered.
- `T-007`: registry validation covers duplicate IDs and invalid family
  definitions.
- `AC-002`: one registry defines concrete handlers and decoder-family order.

### Implemented and verified in the profile-registry slices

- Immutable, protocol-neutral profile contracts have been introduced.
- Generic and television profiles are explicitly registered.
- Profile lookup by ID and stored device type is deterministic.
- Duplicate and structurally invalid profile declarations are rejected.
- A fake profile can be registered and resolved without changing generic
  profile-registry logic.
- Media-player entity eligibility is selected through the profile registry.
- Media-player role aliases and source declarations are profile-owned.
- Ordered role and source resolution is independently testable.
- Command-UI source classification and diagnostics use profile declarations.
- The previous duplicate TV source and role registries have been removed.
- Stored configuration and all v0.6.1 observable media-player behavior remain
  unchanged.

### Implemented and verified in the capability-contract slice

- An immutable generic `ProfileCapability` contract has been introduced.
- Capability definitions are explicitly and deterministically registered.
- Profiles reference capabilities by stable ID.
- Duplicate capability IDs and missing profile capability references are
  rejected.
- The Japanese tuner capability declares its tuner order, selectors, number
  range, routing, state implication, and update policies explicitly.
- Available-tuner detection preserves the existing requirement for a selector
  and at least one tuner-specific numeric command.
- Generic keypad commands can be resolved through a selected tuner with
  normalized command lookup.
- A fake non-TV tuner capability works without tuner-specific registry changes.
- Invalid and duplicate tuner declarations are rejected.
- The regional capability is not attached unconditionally to the base TV
  profile.

## Next implementation slice

Introduce the authoritative codeset-definition registry and deterministic
codeset bindings without changing stored configuration or runtime entity
behavior.

The checkpoint should:

1. Add a dedicated `codesets.py` module containing immutable stable codeset
   definitions.
2. Move codeset metadata ownership out of `infrared_library.py`, including:
   - codeset ID and label;
   - infrared-library module and enum class;
   - base profile ID;
   - optional receive decoder-family ID;
   - ordered capability IDs.
3. Bind all existing codesets to their current base TV profile.
4. Bind the existing receive-capable codesets to their current decoder family.
5. Bind `japanese_tuner` only to `lg_tv_jp`.
6. Add deterministic registry lookup and validation for:
   - duplicate codeset IDs;
   - missing profile references;
   - missing decoder-family references;
   - missing capability references;
   - duplicate capability IDs within a codeset.
7. Preserve the current `infrared_library.py` helper API as a compatibility and
   payload-generation facade while its callers are migrated incrementally.
8. Add tests for production ordering, resolved LG TV Japan bindings, fake
   profiles and capabilities, invalid references, immutability, and existing
   infrared-library behavior.
9. Preserve all stored configuration, generated command payloads, receiver
   behavior, entity behavior, and 100% coverage.

Do not yet migrate `runtime.py`, `select.py`, config entries, or entity setup to
the resolved codeset model. Consume resolved codeset capabilities only after
the codeset registry and compatibility facade are independently green.
